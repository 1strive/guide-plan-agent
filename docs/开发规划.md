# 学习路线驱动的项目开发规划

> 基于你「有一定基础、快速迭代」的选择,本计划从阶段2（Prompt Engineering）开始重点投入,阶段1的核心概念通过代码实践快速覆盖。全周期约 **9 周**(原 10 周;阶段3 RAG 主体被砍后回收约 1 周)。

## 前置：阶段1 基础补强（第1周上半周，3~4天）

虽然你已有基础,但项目还需要补齐一些阶段1的**工程实践**,作为后续阶段的底座。

### Task 1.1：流式输出（Streaming）支持

- **学习目标**:理解推理参数（temperature、max_tokens）对输出的影响;掌握 SSE/流式 API 的设计。
- **项目实践**:在 `src/index.ts` 的 `/sessions/:id/chat` 接口中,增加 `POST /sessions/:id/chat/stream` 端点,使用 `text/event-stream` 返回 LLM 流式输出。
- **关联文件**:`src/index.ts`、`src/agent/llm.ts`
- **输出物**:可运行的流式对话接口;对比实验记录（不同 temperature 的输出差异笔记）。

### Task 1.2：Token 计数与成本控制

- **学习目标**:理解 Token、Tokenizer 概念;建立「按 token 计费」的工程意识。
- **项目实践**:在 `src/agent/llm.ts` 中添加请求/响应 token 估算逻辑（可先用字符数近似,再接入 tiktoken 或 OpenAI 返回的 usage 字段）;记录每次调用的 token 用量到日志。
- **关联文件**:`src/agent/llm.ts`、`src/config.ts`
- **输出物**:带用量统计的日志;单条请求成本计算笔记。

## 阶段2：Prompt Engineering（第1周下半周 ~ 第2周，约10天）

### Task 2.1：提示词版本化与结构化重构

- **学习目标**:掌握「系统提示 vs 用户消息」「角色-任务-约束-输出格式」的结构化写法;建立版本管理意识。
- **项目实践**:重构 `src/agent/prompts.ts`,从单字符串改为**提示词模板引擎**（支持变量插值）,设计多版本提示词存储结构（如 `prompts/v1_base.ts`、`prompts/v2_cot.ts`）。
- **关联文件**:`src/agent/prompts.ts`
- **输出物**:结构化提示词模板;版本切换机制。

### Task 2.2：Few-shot 与 Chain-of-Thought（CoT）提示词

- **学习目标**:理解 Few-shot 示例选取原则;掌握 zero-shot CoT（「让我们一步步想」）的适用边界。
- **项目实践**:
  - 在提示词模板中增加 `examples` 字段,为旅游场景（如「推荐亲子游目的地」）注入 2~3 组 Few-shot 示例。
  - 增加 CoT 模式开关:在系统提示词末尾条件性附加「请逐步分析用户需求,再给出建议」。
- **关联文件**:`src/agent/prompts.ts`、`src/agent/llm.ts`
- **输出物**:两种提示词变体（标准版 vs CoT 版）。

### Task 2.3：Prompt 评测与迭代框架

- **学习目标**:建立「评测意识」——同一提示词用多组输入测试,记录失败案例并迭代。
- **项目实践**:
  - 在项目中新建 `src/eval/` 目录,创建测试集文件（10~30 条旅游问答用例）。
  - 写一个脚本 `scripts/eval-prompt.ts`,批量跑不同版本的提示词,输出准确率、失败案例列表。
  - 用 JSON 记录每次实验:版本号、参数、测试集、通过率、典型失败 case。
- **关联文件**:新增 `src/eval/testset.ts`、`scripts/eval-prompt.ts`
- **输出物**:可复用的 Prompt 评测流水线;至少完成 2 轮迭代记录。

## ⚠️ 阶段3 已废弃(原"RAG 技术",2026-06-01 决定)

**决策**:本项目最终未采用静态 RAG 架构。

**原因**:旅游场景对实时性要求高(开园时间、票价、活动、天气都在变),静态 RAG(seed → chunk → 向量库 → 召回)不适合,改为**阶段4 通过 Skill / MCP 实时调用外部工具**(Tavily web_search 等)动态获取数据,实现"动态 RAG"效果。

**已实施但回滚的内容**(2026-05~06 期间实施,2026-06 删除):

- Task 3.1~3.5:chunker / Embedder 抽象 / Chroma 向量库 / 混合检索 + RRF / sources 溯源
- Task 3.6:Xenova ONNX 本地 embedding(`@xenova/transformers`)
- 配套:`src/rag/` 整目录、`docker-compose.yml` chroma service、`chromadb` + `@xenova/transformers` 依赖、`docs/02-实验记录/exp-04-*`、`docs/03-开发笔记/note-03`

**保留的内容**:

- Task 3.7(web_search)→ 迁到阶段4 入口当 **Task 4.0**(详见下文)
- 整合-1 + 整合-2 全部保留(LangGraph 主线 + Run-as-Resource)
- SQL 工具(`search_destinations` / `get_destination_detail`)+ MySQL seed → 暂留作为阶段4 MCP 真正接入前的本地工具;阶段4 完成 MCP 接入后再清(用户决策)

**面试讲法**(STAR):学了 RAG 八股 → 实施全套 → 实测发现旅游场景不适合(数据静态 vs 业务实时) → 决定改用 MCP 动态获取 → 回滚 RAG 代码 → 反映"技术选型必须匹配业务特征"的工程判断力。

> **学习材料保留**:`docs/01-面试八股文/03-RAG技术.md` 作为面试知识点保留,文件顶部加"本项目未采用"框注。

## 整合阶段:LangGraph 主线切换 + 会话续流(承上启下)

> **本阶段不属于阶段2 也不属于阶段4,是横跨二者的"框架整合"**。背景:阶段2 完成后,真实使用反馈出会话续流的强需求(切走会话不应丢任务),手写实现成本相当于 Task 4.5 完整复杂度;借力 LangGraph 的 `thread_id` + `Checkpointer`,接框架的工程成本远低于手写。所以决定**先切到 LangGraph 主线(整合-1)+ 用 LangGraph 现成能力一次性做 Run-as-Resource 完整版(整合-2,吸收原 Task 4.5)**,然后接 Task 4.0(web_search)→ 进阶段4(精简为 4.1/4.2/4.3/4.4)。
>
> **执行顺序**:Task 1.1~2.3(✅ 已完成)→ **Task 整合-1(✅ 已完成)→ Task 整合-2(✅ 已完成)** → Task 4.0 web_search(✅ 已完成) → 阶段4(4.1~4.4)。
>
> **取消/合并的旧任务**:① Task 4.6"LangGraph 对照实现"取消(整合-1 已切主线);② Task 4.5"Run 持久化完整版"整体并入整合-2。理由见关键设计决策 #6 升级版。

### Task 整合-1:切换主 Agent 为 LangGraph(主线替换)

- **学习目标**:掌握 `langchain.createAgent` 的实际使用 + StateGraph + Checkpointer 的"持久状态"心智;学会 LangGraph 事件流与 AG-UI 协议的 **adapter** 写法;真正理解"为什么大厂选 LangGraph 不只是为了 `createAgent`,而是为了 `thread_id` + `Checkpointer` 给状态管理铺的路"。
- **背景说明**:原 Task 4.6 设想"手写主线 + LangGraph 对照"。但整合阶段要做"会话续流"(Task 整合-2),**LangGraph 的 thread_id + Checkpointer 让续流实现成本远低于手写**——所以决定**在整合阶段先切到 LangGraph 主线**,Task 4.6 取消。这是真实工程常见决策:发现某能力靠手写做要 2 周、接框架只要 2 天,就该接框架。
- **技术选型决定**:
  - LangGraph 核心:`langchain` 包的 `createAgent`(LangChain 1.x 推荐 API,原 `createReactAgent` 已 deprecated)
  - Checkpointer:开发用 `MemorySaver`(进程内),整合-2 升级到 `SqliteSaver` 或自研 `MySQLSaver`
  - LLM 适配:`@langchain/openai`(MiniMax 走 OpenAI 兼容协议)
  - **保留 AG-UI 事件协议**,写 adapter 翻译 LangGraph 的 `streamEvents` v2 输出
- **项目实践**:
  - **依赖**:`npm i langchain @langchain/core @langchain/langgraph @langchain/openai`
  - **核心实现**(新增 `src/agent/langgraph-agent.ts`,目标 < 200 行):
    - 用 `createAgent` 注册当时的 2 个工具(`search_destinations` / `get_destination_detail`);Task 4.0 完成后再加 `web_search`
    - 工具用 zod schema 定义(LangGraph 标准),复用现有 `runTool` 的实现逻辑
    - 用 `MemorySaver` 作 Checkpointer,`thread_id = sessionId`
    - 流式输出走 `agent.streamEvents(input, { version: 'v2', configurable: { thread_id }})`
  - **事件 Adapter**(新增 `src/agent/langgraphToAgUi.ts`):
    - 把 LangGraph 的 `on_chat_model_stream / on_tool_start / on_tool_end / on_chain_end` 翻译成项目原生 AG-UI 事件(RUN*STARTED / TEXT_MESSAGE*_ / TOOL*CALL*_ / RUN_FINISHED)
    - 保持前端 SSE 协议**完全不变**(前端无感切换 backend)
    - 保持 `RUN_FINISHED.sources` 字段(从工具结果聚合,逻辑跟手写时一致)
    - 保持 `[ASK_USER]` 协议检测(在 adapter 层做,**不立即升级到 LangGraph 原生 `interrupt()`**,留给整合-2 评估)
  - **handler 切换**:`src/index.ts` 的 `POST /sessions/:id/stream` 改调 `runLangGraphAgent`;**原手写的 `runAgentStream` 完整删除**(STAR 故事写笔记,不留死代码)
  - **prompts 不变**:LangGraph 同样接受 system prompt + Few-shot prepend messages,`v1_base` 全套约束直接复用
  - **tools.ts 不变**:工具实现复用,只是注册到 LangGraph 而非自己手写循环调用
  - **sanitize 不变**:入口 / 出口 detectInjection / wrapUntrusted 仍在 handler 层做,跟 backend 解耦
- **关联文件**:
  - 新增 `src/agent/langgraph-agent.ts`、`src/agent/langgraphToAgUi.ts`
  - 修改 `src/index.ts`(handler 切换);删除 `src/agent/llm.ts` 中的 `runAgentStream`;`package.json` 加 4 个 LangChain 依赖
- **关联八股**:
  - 02-核心框架.md §6 LangGraph 状态机 / Q9~Q11 何时选 LangGraph
  - 02-核心框架.md ReAct 循环(手写 vs `createAgent` 的对比)
- **关键决策与边界**:
  - ✅ **主线切换,不保留双 backend**:原 Task 4.6 "并存对照"取消
  - ✅ **保留 AG-UI 协议**:adapter 层吸收 LangGraph 事件差异,前端 0 改动、评测脚本 0 改动
  - ✅ **删除手写代码**:`runAgentStream` 完整删除,`src/agent/llm.ts` 瘦身为只导出 `ChatMessage` / `ResumeItem` / `TokenUsage` 类型;STAR 故事("手写 vs LangGraph 对比")写在 `docs/03-开发笔记/note-04` 而不是靠源码留档
  - ✅ **MemorySaver 起步**:Checkpointer 用最简单的进程内实现,整合-2 再升级到持久化存储
  - ❌ **不引入 LangChain 全家桶**:只装 `langchain` + `@langchain/core` + `@langchain/langgraph` + `@langchain/openai` 四个最小包
  - ❌ **不立即用 LangGraph 原生 `interrupt()`**:`[ASK_USER]` 字符串协议先保留,整合-2 评估是否升级
- **输出物**:
  - ① LangGraph 主路径可演示对话(同测试集 + 前端 + 评测脚本零侵入切换通过)

### Task 整合-2:Run-as-Resource(完整版,吸收原 Task 4.5 全部能力)

- **学习目标**:理解"HTTP 请求 ≠ Agent Run"的解耦原则;掌握长任务系统的事件回放、订阅恢复、三态 abort(被动断开 / 主动取消 / 系统关停)的工程实现;建立"Run-as-Resource"心智模型(对标 LangGraph runs / OpenAI Assistants threads);借力 LangGraph `thread_id` + 持久化 Checkpointer 实战。
- **背景说明**:原计划"轻量版整合-2 + 完整版 Task 4.5"两步走;决策升级为**一次性做完整版**——理由:轻量版基础设施(runRegistry、DB 表、handler 改造)和完整版重叠 70%,拆两步会产生重复工作 + 接口反复调整。整合-1 切到 LangGraph 后,Checkpointer + thread_id 都是现成的,正好一次性把"Run-as-Resource"做透。**Task 4.5 整体被吸收,阶段4 不再做**(见关键设计决策 #6 升级版)。
- **依赖**:Task 整合-1(LangGraph 主线必须先就绪)。
- **覆盖 5 大需求集**:
  - 【**A. 切走不停 + 续订**】(原"轻量版"4 条需求)
    1. 前端:切换会话后旧会话 SSE 必须停(reader.cancel + AbortController per session)
    2. `GET /messages` 加 `status` 字段;running 时前端续流带 `lastEventSeq`
    3. 客户端断开 ≠ abort Run;Run 在内存继续跑 + 持续写库;完成后 status 转 'completed'
    4. 续流时对比 seq,补发缺失事件
  - 【**B. 主动取消**】(原 Task 4.5) 5. 前端显式"停止"按钮 → `POST /sessions/:id/runs/:runId/cancel`(202 Accepted,幂等) 6. 三态 AbortController 模型:per-subscriber(req close → 仅 unsubscribe)vs per-run(cancel/SIGTERM/超时 → 真 abort)**两个 controller 无级联**
  - 【**C. 事件级 seq 回放**】(原 Task 4.5) 7. 每条 AG-UI 事件写 `agent_run_events(run_id, seq, event_json)`;同事件序列回放结果可重复且与首次完全一致8. `GET /sessions/:id/runs/:runId/stream?after_seq=N` 续订接口:先回放 N 之后的事件,再接实时流
  - 【**D. 完整状态机 + 多订阅者**】(原 Task 4.5) 9. 状态机:`pending → running → {completed | interrupted | cancelling → cancelled | failed}` 10. 同一 Run 支持多个订阅者并发续订(多 tab 打开同会话)
  - 【**E. 持久化 Checkpointer + 进程重启降级**】(原 Task 4.5) 11. LangGraph Checkpointer 从 MemorySaver 升级到 `@langchain/langgraph-checkpoint-sqlite` 的 SqliteSaver(或自研 MySQLSaver,跟 chat_sessions 同库) 12. 进程重启:扫描 `agent_runs.status='running'` 全标 `failed`;前端续订时显式提示"由于服务重启,本次任务已中断"(Redis Pub/Sub 跨进程方案推迟到 Task 5.4 容器化)
- **项目实践**:
  - **DB 改动**(新增 `src/db/migrations/003_agent_runs_events.sql`):
    - `chat_sessions` 加 `status ENUM('running','end') NOT NULL DEFAULT 'end'`(简化版,供 /messages 快查)
    - **新表 `agent_runs(run_id PK, session_id, status, started_at, finished_at, last_event_seq, total_tokens)`**,完整状态机
    - **新表 `agent_run_events(run_id, seq PK part, event_json, created_at)`**,事件流水
    - 启动清理:`UPDATE agent_runs SET status='failed' WHERE status IN ('pending','running','cancelling')`
  - **DB 仓**:扩展 `src/db/chatRepo.ts`(status 字段) + 新增 `src/db/runRepo.ts`(agent_runs / agent_run_events CRUD + seq 自增 + 回放查询)
  - **核心新模块 `src/agent/runManager.ts`**(进程内 Run 注册表):
    - `start(sessionId, runInput) → runId` — 创建 Run,启动 LangGraph,挂上 per-run AbortController,事件实时写 agent_run_events
    - `subscribe(runId, onEvent) → unsubscribe` — 加订阅者,可多个;断开只 unsubscribe 不 abort
    - `cancel(runId)` — 触发 per-run AbortController + status='cancelling'→'cancelled'
    - `getActive(sessionId)` — 查最近未完成 Run
    - 三态 abort 模型:per-subscriber Controller + per-run Controller,**互不级联**
  - **Checkpointer 升级**:换 LangGraph 的 `@langchain/langgraph-checkpoint-sqlite` SqliteSaver(或自研 MySQLSaver 跟 chat_sessions 同库,如果想统一);进程重启后 LangGraph 自身的 thread 状态也能恢复
  - **handler 改造**(`src/index.ts`):
    - `POST /sessions/:id/stream`:改为 `runManager.start + subscribe`(不再阻塞读 LangGraph 流自己 yield)
    - `GET /sessions/:id/runs/active` — 返回最近未完成 Run 或 null
    - `GET /sessions/:id/runs/:runId/stream?after_seq=N` — 续订:`runRepo.queryEvents(runId, after_seq)` 回放 + `runManager.subscribe(runId)` 接实时
    - `POST /sessions/:id/runs/:runId/cancel` — `runManager.cancel(runId)`,202 + 幂等
    - `GET /sessions/:id/messages` 加 status 字段(从 chat_sessions 直查)
    - `req.raw 'close'` 钩子:改为 `runManager.unsubscribe(runId, subscriberId)`,**不再 ctl.abort()**
  - **Adapter 改造**(`src/agent/langgraphToAgUi.ts`):
    - 每 yield 一个 AG-UI 事件,同步调 `runRepo.appendEvent(runId, seq++, event)`
    - LangGraph 的 `on_chat_model_stream` 聚合到 assistant 消息时增量 update `chat_messages`(避免每 token 一行)
    - `on_chain_end` 时:`runManager.complete(runId)` + 更新 chat_sessions.status='end' + agent_runs.status='completed'
  - **前端配套**(`web/src/api.ts` + `web/src/App.tsx`):
    - `switchSession` 持 AbortController,切前 `abort()` + reader.cancel
    - 打开会话 → `GET /runs/active` → 有活跃 Run 则用 `?after_seq=last_seq` 续订;无则走历史接口
    - 加显式「停止」按钮 → `POST /cancel`
  - **架构文档同步**:`docs/04-架构文档/agent-架构.md` §3.3(中断处理改写)、§6 局限表移除"切走会话=任务终止"等多条、§1.1 分层图加 runManager
- **关联文件**:
  - 新增 `src/db/migrations/003_agent_runs_events.sql`、`src/db/runRepo.ts`、`src/agent/runManager.ts`
  - 修改 `src/db/chatRepo.ts`、`src/agent/langgraph-agent.ts`、`src/agent/langgraphToAgUi.ts`、`src/index.ts`(多个新路由 + 现有路由改造)、`web/src/api.ts`、`web/src/App.tsx`
  - 依赖:`npm i @langchain/langgraph-checkpoint-sqlite`(或不装,自研 MySQLSaver 跟 chat_sessions 同库)
- **关联八股**:
  - 02-核心框架.md ReAct 循环 / Run-as-Resource 模型
  - 05-记忆系统.md §短期记忆(agent_run_events = episodic memory 的工程形态)
  - 08-工程化实践.md §1 容错(细粒度 abort)/ §3 全链路可观测(事件日志即审计源)
- **关键决策与边界**:
  - ✅ **完整三态 abort 模型**:per-subscriber 仅 unsubscribe,per-run 才真 abort
  - ✅ **事件级 seq 回放可重复**:同事件序列回放结果与首次完全一致
  - ✅ **持久化 Checkpointer**:进程重启后 LangGraph thread 状态可恢复(但运行中 Run 仍标 failed,见下)

  - ❌ **跨进程方案(Redis Pub/Sub)推迟到 Task 5.4 容器化阶段**
- **输出物**:
  - ① 可演示完整链路:切走 → 主动停 → 回来 → 重启等各场景下的行为正确
  - ② 12 个具体需求逐条对应的验证步骤

### Task 4.0:外部工具基础(web_search via Tavily)

- **学习目标**:理解 Agent "外部世界感知" 的工程模式;掌握第三方 API 工具的接入、缓存、配额管理;从"封闭数据库 demo"升级到"开放数据源 Agent",这是项目走出"玩具感"的关键一步,也是后续 Task 4.4 MCP/Skills 体系的核心数据源。
- **背景说明**:本任务原为 Task 3.7,在阶段3 RAG 主体废弃后(决策见上)迁入阶段4。当前知识库只有 3 个目的地(`scripts/seed.ts` 硬编码),Agent 永远只能推荐成都/丽江/哈尔滨。本任务接入联网搜索,让 Agent 能回答任意目的地的实时问题(如"东京 12 月有什么活动")。**注意**:这不是删除 SQL 工具,而是**加一条新工具路径**——SQL/Web 双路共存,模型按场景选;Task 4.4 会把它们统一封装为 MCP Server,并引入更多 MCP source 实现"动态 RAG"。
- **技术选型决定**:使用 **Tavily Search API**(`@tavily/core`)。理由:① 专为 LLM 设计,返回的就是清洁文本片段(不像 Google/Bing 返回 HTML 要再 parse);② 免费额度 1000 次/月,学习项目够;③ 内置 `topic` / `time_range` / `include_answer` 等 LLM 友好参数;④ 业界主流(LangChain、CrewAI 默认集成),面试讲选型时有共识。
- **项目实践**:
  - **依赖与配置**:`npm i @tavily/core`;`.env` 增加 `TAVILY_API_KEY`;`config.ts` zod 化(`TAVILY_API_KEY` optional、`WEB_SEARCH_CACHE_TTL_SECONDS` 默认 86400)。
  - **新增 `web_search` 工具**(`src/agent/tools.ts`):参数 `{ query, max_results?, search_depth? }`,返回带 url + title + snippet 的结构化结果。
  - **缓存层**:`src/agent/webSearchCache.ts` 用 MySQL 表 `web_search_cache(cache_key CHAR(64) PK, response_json, created_at)`,cache_key = SHA-256(query + depth),TTL 默认 24h——同问题不重复烧 Tavily 额度。迁移文件 `src/db/migrations/004_web_search_cache.sql`。
  - **Source 类型扩展**:`Source` 升级为 discriminated union `DestinationSource | UrlSource`;`UrlSource` 含 `{ url, title, snippet, via: 'web_search' }`,前端按 `type` 渲染。
  - **跨工具 sourceMap**:`langgraph-agent.ts` 用 `sourceKey(s)` 把 destination/url 两类 source 统一进 `Map<string, Source>`(key = `dest-${id}` 或 `url-${url}`),`RUN_FINISHED.sources` 输出去重后的全集。
  - **system prompt 更新**(`v1_base.toolUsageRules`):新增"当问题涉及实时信息(开园时间、活动、价格、当前天气等)或数据库不覆盖的目的地时,调用 `web_search`"。
  - **注入防御扩展**:Web 检索结果是间接注入高危区(网页可能含 prompt injection),返回的每条 snippet 都走 `detectInjection` + `wrapUntrusted`(`src/agent/sanitize.ts` 复用)。
  - **无 key 友好降级**:`TAVILY_API_KEY` 未配置时 `web_search` 返回明确提示消息,让模型回退到 SQL 工具或如实告知用户"无法联网"。
  - **测试集扩充**:`testset.ts` 新增 5 条 `web-*` case,如「北京 2026 年春节有什么活动」「东京 12 月推荐景点」,全部标 `knownFail`(无 key 时不计硬失败)。
- **关联文件**:`src/agent/tools.ts`、`src/agent/prompts/v1_base.ts`、`src/agent/sanitize.ts`(复用)、新增 `src/agent/webSearchCache.ts`、`src/db/migrations/004_web_search_cache.sql`、`src/eval/testset.ts`、`src/agent/ag-ui.ts`(Source union 化)、`src/agent/langgraph-agent.ts`(sourceKey + wrap web_search)
- **关联八股**:
  - 04-工具调用.md §3 外部 API 工具 / §5 缓存与配额
  - 08-工程化实践.md §4 间接注入防御(Web 是高危源)
- **输出物**:可演示的"问任意目的地"能力(对照之前只能答 3 个目的地的尴尬);Web 注入防御实测;Tavily 调用成本日志。
- **后续衔接**:Task 4.4 会把 `web_search` / `get_destination_detail` / `search_destinations` 统一封装为 MCP Server,并扩展更多 MCP source(高德地图、和风天气等)实现"动态 RAG"——查询时拉最新数据,不维护离线索引。

### Task 4.4：MCP（Model Context Protocol）接入 + Agent Skills + 动态 RAG

- **学习目标**:理解 MCP 与「普通 function calling」在架构上的区别;掌握 **Agent Skills** 模型(把若干 tools + prompt 打包成可复用能力,对标 Anthropic Agent Skills / Claude Code skills);能讲清楚"工具(Tool)→ 工具集(Server)→ 技能(Skill)"三层抽象的演进路径;**理解"动态 RAG via MCP"如何替代静态 RAG**。
- **背景说明**:Task 4.0 之后,Agent 有 SQL × 2 + Web × 1 共 3 个工具,散在本地代码。本任务做三件事:
  1. 把它们都搬到 MCP Server,跨进程标准化;
  2. 接入更多外部 MCP source(高德地图 / 和风天气 / 携程等),让 Agent 能查实时景点信息、天气、票价——这就是"动态 RAG"的具体形态(查询时拉数据,不维护索引);
  3. 用 Skill 概念把它们组合成"旅游推荐"等可复用能力包,模型选用 Skill 而非散选 tool,大幅降低决策复杂度。
- **项目实践**:
  - **MCP Server 化**(新增 `src/mcp/servers/`):
    - `destinationServer.ts`:封装 `get_destination_detail` + `search_destinations`(走 stdio 传输)
    - `webSearchServer.ts`:封装 `web_search`(走 stdio 传输)
    - 共用 schema 校验、错误处理、token 计数中间件
  - **MCP Client**(新增 `src/mcp/client.ts`):Agent 侧实现,启动时连接所有配置的 MCP server,把它们暴露的 tools 注册到 LLM 的 function calling schema
  - **跑通外部 MCP**:至少接入 2 个外部 MCP source(候选:`@modelcontextprotocol/server-filesystem` 验证兼容性;高德地图 MCP / 和风天气 MCP 验证"动态 RAG"实战),让 Agent 能查实时旅游信息
  - **Agent Skills 落地**(新增 `src/skills/`):
    - 每个 Skill 是一个文件夹,含 `SKILL.md`(描述何时触发 + 使用的 tools + system prompt 片段)+ 可选 `examples/` Few-shot
    - 至少落地 2 个 Skill:
      - `travel-recommend/`:组合 `web_search` + 高德地图 + `get_destination_detail`,做"问任意目的地"的旅游推荐
      - `local-research/`:组合 filesystem + web_search,做本地文档调研(展示 Skill 的非旅游适用性)
    - **Skill Loader**(`src/skills/loader.ts`):启动时扫描 `src/skills/` 目录,把每个 SKILL.md 注入到 system prompt 的可选段落,模型根据用户意图决定加载哪个 Skill
    - 参考实现:Anthropic Agent Skills 规范(https://docs.claude.com/en/docs/agents-and-tools/agent-skills)
  - **seed.ts 清理时机**:MCP 接入完成后,SQL 工具(`search_destinations` / `get_destination_detail`)若已被高德地图 MCP 等动态 source 替代,**删除 `scripts/seed.ts` + MySQL `destinations` / `destination_features` 表 + 两个 SQL 工具**(用户原话:"等稍后实现阶段4 后,再删除 scripts/seed.ts 的关联链路");若 MCP source 没完全覆盖,本地 seed 暂留兜底
  - **prompts 更新**:`v1_base` 增加 `skillRegistry` section,枚举可用 Skill 名称 + 一句话触发条件
  - **评测扩展**:`testset.ts` 加 `skill-*` case,验证模型能选对 Skill;考察"启用 vs 关闭 Skill"时同 case 的决策质量
- **关联文件**:新增 `src/mcp/(servers|client.ts)`、`src/skills/{travel-recommend,local-research}/`、`src/skills/loader.ts`、`src/agent/prompts/v1_base.ts`(skillRegistry section);酌情删除 `scripts/seed.ts` / `src/db/destinationRepo.ts` / `search_destinations` + `get_destination_detail` 工具
- **关联八股**:
  - 04-工具调用.md §6 MCP 协议 / §7 Agent Skills 抽象
  - 02-核心框架.md §Tool ecosystems(工具 → MCP → Skill 三层抽象)
- **输出物**:
  - ① 2 个自研 MCP Server + 2 个外部 MCP Server 接入演示
  - ② 2 个可工作的 Skill;开/关 Skill 的决策质量对比数据
  - ③ 一段"为什么 Skill 比直接给一堆 tool 更好 + 动态 RAG 为什么比静态 RAG 更适合实时数据场景"的技术决策记录(对应面试 STAR 故事)

### Task 5.5：LLM 网关层抽象（AI Gateway）

- **学习目标**:理解 AI 网关的定位与职责(统一接入、路由、缓存、限流、降级、可观测、合规),掌握中间件链式架构在 LLM 调用场景的落地方式;能讲清楚「自研轻量网关 vs LiteLLM/Portkey/Cloudflare AI Gateway 等成熟方案」的取舍。
- **背景说明**:Task 1.2(token 统计)、5.2(模型路由)、5.3(容错监控)的能力分散在各处。本任务的目标是把这些跨切面能力**收口到一个网关层**,使业务代码(Agent、MCP、Planner)不再感知 Provider 差异。
- **项目实践**:
  - **接口抽象**:新建 `src/gateway/` 目录,定义统一接口 `LLMGateway.chat(req): Promise<ChatResponse>` 与流式接口 `chatStream(req)`,业务代码改为依赖该接口而非直连 Provider SDK。
  - **中间件链路**:实现可组合的中间件管道 `request → router → cache → ratelimit → provider adapter → retry → metrics → response`,每一层职责单一、可独立开关。
  - **多 Provider 适配器**:至少实现 2 个 adapter(如 MiniMax + OpenAI 兼容协议),通过配置切换,证明抽象有效。
  - **响应缓存 MVP**:对相同 messages 做哈希,命中直接返回缓存响应;缓存可先用内存 LRU 或 MySQL 落盘。
  - **限流与配额**:基于 user_id / session_id 的滑动窗口限流;预留按 project 维度的预算上限(超额拒绝或降级到轻量模型)。
  - **统一可观测**:在网关入口生成 `trace_id`,串联 router 决策、cache 命中、retry 次数、provider 名、token 用量、总延迟;输出结构化日志。
  - **整合既有任务**:将 Task 5.2 的 router、Task 5.3 的 retry/metrics 重构为网关中间件而非散落在原模块。
- **关联文件**:新增 `src/gateway/index.ts`、`src/gateway/middleware/{router,cache,ratelimit,retry,metrics}.ts`、`src/gateway/providers/{minimax,openai}.ts`;重构 `src/agent/langgraph-agent.ts` 走网关接口。
- **对照实验**:开关「响应缓存」「智能路由」前后,统计相同测试集的成本(token 消耗)、平均延迟、缓存命中率;写入 benchmark。
- **输出物**:可插拔中间件的网关层;多 Provider 切换 Demo;带缓存/路由前后对比的实验数据;一段能讲清楚「为什么需要网关、自研还是用 LiteLLM」的技术决策记录。

## 关键设计决策说明

1. **为什么从阶段2开始,阶段1只补 3~4 天?**
   项目已有 LLM 调用和 API 基础,阶段1的核心概念(Transformer、Token、参数)可通过「流式输出 + Token 统计」这两个小任务快速覆盖,不需要单独花整周时间。

2. **为什么阶段4要同时保留 ReAct 和 Plan-and-Execute?**
   面试问答集 Q1 就是「为什么选择 ReAct 而不是 Plan-and-Execute」。项目中同时实现两种模式并支持切换,既能深入理解两者差异,又能在面试中用实际数据(步骤数、耗时、完成率)支撑回答。

3. **为什么阶段4要把 Run 持久化(整合-2)和记忆分层(4.3)绑在一起?**
   两者本质都在回答"什么状态需要跨连接、跨会话存活"——整合-2 处理"事件流水"(episodic 记忆),4.3 处理"语义摘要"(semantic 记忆),共用 `agent_runs` 持久层、共用 `RUN_FINISHED` 触发时机。技术上整合-2 是 4.3 的底座(摘要生成需要订阅 Run 完成事件);面试上这对组合能直接对应八股 05 §短期/长期记忆,是非常完整的故事点。同时整合-2 还纠正了阶段1"客户端断开即终止 Run"的 Chat App 心智,把项目从"对话工具"提升为"Run-as-Resource"的 Agent 系统——这是阶段3~5 工程化故事的关键转折。

4. **为什么阶段5要单独抽出 LLM 网关层(Task 5.5)?**
   网关层是大厂 LLM 应用必备的工程化能力,能在一处集中处理「统一接入、路由、缓存、限流、降级、可观测、合规」等跨切面问题。Task 1.2、5.2、5.3 的能力如果散落在各处,面试时只能讲点状能力;而把它们收口为一个网关,可以同时覆盖「架构分层」「中间件模式」「成本治理」「可观测性」「降级容错」5 个常考点,是性价比最高的工程化故事点。同时本任务也对应面试中「自研 vs LiteLLM/Portkey 等成熟方案如何取舍」的高频问题。

5. **为什么把 LangGraph 主线切换 + Run-as-Resource 完整版都拆成"整合阶段"?**
   三个原因:① **范围边界**——这两件事是横跨"阶段2 已建的工具/sanitize/prompts"和"阶段4 即将做的 ReAct 增强/MCP"的横切面改动,塞任一阶段都会稀释叙事;独立成"整合阶段"让两侧都干净。② **接框架降本**——整合-2 的会话续流需求(切走 Run 不停、主动取消、事件回放等)如果靠手写实现就是 Task 4.5 的全部复杂度;LangGraph 的 `thread_id` + 持久化 Checkpointer 是现成的,**接框架的成本远低于手写**——所以决定整合-1 先切 LangGraph 主线(Task 4.6 取消),整合-2 在 LangGraph 基础上一次性做 Run-as-Resource 完整版。③ **一次到位 vs 两步走**——最初规划"整合-2 轻量版 + Task 4.5 完整版"两步;后改为整合-2 直接做完整版(Task 4.5 整体并入),理由是轻量版基础设施(runRegistry、DB 表、handler 改造)和完整版重叠 70%,拆两步会产生重复工作 + 接口反复调整。**手写 `runAgentStream` 直接删除**(不保留作历史参考——STAR 故事写在 `docs/03-开发笔记/note-04` 即可,源码留档反而成腐烂死代码),"手写 vs LangGraph 对比" STAR 故事在整合-1 输出物里讲——这是真实工程常见决策:**发现某能力靠手写要 2 周、接框架只要 2 天,就该接框架**;**发现"轻量版 + 完整版两步走"会重复造轮子,就一次做完整版**。阶段4 因此简化为 4.0/4.1/4.2/4.3/4.4 五个任务。

6. **为什么阶段3 RAG 主体被废弃?(2026-06-01 决策)**
   **学了 → 实施了 → 实测后判定不适合 → 回滚**。RAG 八股完整覆盖(切分、Embedder 抽象、Chroma、混合检索 + RRF、Xenova ONNX 本地 embedding),代码全部实现并提交(commit `8502d52` ~ `ea485e8` 5 个 commit)。但实施后判定:**旅游场景的核心数据(开园时间、票价、活动、天气)是高频变动的**,静态 RAG 的"离线索引 + 召回"范式不适合——索引一旦灌完,数据就开始过期。改为**阶段4 通过 MCP/Skills 实时调用外部工具**(Tavily、高德、和风等)动态获取数据,本质上实现了"动态 RAG"(查询时拉数据,而非预先索引)。**这个决策本身是项目的优质 STAR 故事**:反映"技术选型必须匹配业务特征"的工程判断力,且面试讲述时学过 RAG 八股仍然可用——只是讲清楚"为什么学了但不用"。RAG 代码 git 历史保留,八股 `docs/01-面试八股文/03-RAG技术.md` 保留并加"本项目未采用"框注。

7. **为什么 Task 4.4 把 MCP 和 Agent Skills 绑在一起?**
   单独看 MCP 是协议升级(本地直调 → 跨进程调用),收益主要在工程层(工具复用、跨语言);单独看 Skills 是抽象升级(散乱 tool → 组合能力包),收益主要在模型层(决策复杂度降低)。**两者绑在一起讲**才能完整对应"工具(Tool)→ 工具集(Server)→ 技能(Skill)"三层抽象的演进——这是 2025 年 Agent 工程的最重要趋势,且能直接对接 Anthropic Agent Skills / Claude Code skills 等业界规范。另外 Task 4.4 也是**"动态 RAG"的真正落地点**——把外部 MCP source(高德、和风、Tavily)组合成 Skill,模型按场景调用,实现"查询时拉最新数据"的检索增强,这是对决策 #6"为什么放弃静态 RAG"的工程兑现。

8. **每个阶段的「输出物」是什么?**
   每阶段至少产出:① 可运行的代码 + ② 笔记/实验记录 + ③ 一个能对外演示的效果。阶段6 产出简历条目和面试故事。
