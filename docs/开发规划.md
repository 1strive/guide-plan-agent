> 基于你「有一定基础、快速迭代」的选择，本计划从阶段2（Prompt Engineering）开始重点投入，阶段1的核心概念通过代码实践快速覆盖。全周期约 **10 周**。

## 前置：阶段1 基础补强（第1周上半周，3~4天）

虽然你已有基础，但项目还需要补齐一些阶段1的**工程实践**，作为后续阶段的底座。

### Task 1.1：流式输出（Streaming）支持
- **学习目标**：理解推理参数（temperature、max_tokens）对输出的影响；掌握 SSE/流式 API 的设计。
- **项目实践**：在 `src/index.ts` 的 `/sessions/:id/chat` 接口中，增加 `POST /sessions/:id/chat/stream` 端点，使用 `text/event-stream` 返回 LLM 流式输出。
- **关联文件**：`src/index.ts`、`src/agent/llm.ts`
- **输出物**：可运行的流式对话接口；对比实验记录（不同 temperature 的输出差异笔记）。

### Task 1.2：Token 计数与成本控制
- **学习目标**：理解 Token、Tokenizer 概念；建立「按 token 计费」的工程意识。
- **项目实践**：在 `src/agent/llm.ts` 中添加请求/响应 token 估算逻辑（可先用字符数近似，再接入 tiktoken 或 OpenAI 返回的 usage 字段）；记录每次调用的 token 用量到日志。
- **关联文件**：`src/agent/llm.ts`、`src/config.ts`
- **输出物**：带用量统计的日志；单条请求成本计算笔记。

## 阶段2：Prompt Engineering（第1周下半周 ~ 第2周，约10天）

### Task 2.1：提示词版本化与结构化重构
- **学习目标**：掌握「系统提示 vs 用户消息」「角色-任务-约束-输出格式」的结构化写法；建立版本管理意识。
- **项目实践**：重构 `src/agent/prompts.ts`，从单字符串改为**提示词模板引擎**（支持变量插值），设计多版本提示词存储结构（如 `prompts/v1_base.ts`、`prompts/v2_cot.ts`）。
- **关联文件**：`src/agent/prompts.ts`
- **输出物**：结构化提示词模板；版本切换机制。

### Task 2.2：Few-shot 与 Chain-of-Thought（CoT）提示词
- **学习目标**：理解 Few-shot 示例选取原则；掌握 zero-shot CoT（「让我们一步步想」）的适用边界。
- **项目实践**：
  - 在提示词模板中增加 `examples` 字段，为旅游场景（如「推荐亲子游目的地」）注入 2~3 组 Few-shot 示例。
  - 增加 CoT 模式开关：在系统提示词末尾条件性附加「请逐步分析用户需求，再给出建议」。
- **关联文件**：`src/agent/prompts.ts`、`src/agent/llm.ts`
- **输出物**：两种提示词变体（标准版 vs CoT 版）。

### Task 2.3：Prompt 评测与迭代框架
- **学习目标**：建立「评测意识」——同一提示词用多组输入测试，记录失败案例并迭代。
- **项目实践**：

  - 写一个脚本 `scripts/eval-prompt.ts`，批量跑不同版本的提示词，输出准确率、失败案例列表。
  - 用 JSON 记录每次实验：版本号、参数、测试集、通过率、典型失败 case。
- **关联文件**：新增 `src/eval/testset.ts`、`scripts/eval-prompt.ts`
- **输出物**：可复用的 Prompt 评测流水线；至少完成 2 轮迭代记录。

## 阶段3：RAG 技术（第3周 ~ 第4周，约2周）

> 当前 `src/rag/` 为空，且系统提示词中提到了 `semantic_search_travel` 工具但 **尚未实现**，这是本阶段的核心战场。

### Task 3.1:文档切分与 Embedding 抽象
- **学习目标**:理解 chunk 大小、overlap 对检索质量的影响;掌握 embedding **多 provider 抽象**的工程价值(本任务真实工程教训:MiniMax 账号无 embedding 权限,逼出抽象层)。
- **项目实践**:
  - **切分**:从 `destinations` + `destination_features` 表生成 chunk(`src/rag/chunker.ts:buildAllChunks`)。
    - 策略:1 个 summary chunk + 每条 feature 各 1 chunk;**不做 overlap**(条目独立无上下文关联,overlap 反而引入噪声)。
    - **chunk text 自带前缀**:`"丽江的美景「玉龙雪山」:..."` 让 chunk 自我描述完整,不依赖外部上下文。
    - metadata 字段:`{ destinationId, destinationName, region, category, source }`,给 Chroma `where` 过滤和 Task 3.5 溯源用。
  - **Embedder 抽象**(`src/rag/embedder.ts`):统一接口 `generate(texts: string[]) → number[][]`(与 chromadb `EmbeddingFunction.generate` 对齐),工厂函数 `createEmbedder(config)` 按 `EMBEDDING_PROVIDER` 实例化。
  - **三档实现**:
    - `MinimaxEmbedder`:走 `embo-01`,需 token plan 支持(**当前 MiniMax 测试账号不支持,会 throw**——这是抽象层必须存在的根因)。
    - `OpenAIEmbedder`:走标准 `/embeddings` 协议(`text-embedding-3-small`,1536 维),需真 OpenAI key。
    - `DeterministicEmbedder`:**字符 2-gram + 3-gram → FNV-1a 哈希 → L2 归一化**(128 维,完全离线、零依赖、可复现)。**作为 dev/演示默认**——让 RAG 全链路在无任何外部 embedding 服务时也能跑通。
  - 注:本任务**不接入真模型**,只把抽象层和 deterministic fallback 落地;真模型在 Task 3.6 接入(Transformers.js + Xenova/bge-small-zh-v1.5 本地 ONNX)。
- **关联文件**:新增 `src/rag/types.ts`、`src/rag/chunker.ts`、`src/rag/embedder.ts`
- **关联八股**:
  - 03-RAG技术.md §2 切分策略 / §3.1 embedding 模型选型
  - 08-工程化实践.md §5 多 Provider 抽象(本任务是抽象的诞生)
- **输出物**:切分后的 chunk 数据集(18 条);3 个 Embedder 实现 + 工厂函数;一段"为什么 Embedder 必须抽象(MiniMax 无权限事件复盘)"的设计决策记录(写入代码注释或 `docs/03-开发笔记/note-03 §2`)。

### Task 3.2：向量存储与检索（Chroma）
- **学习目标**：掌握向量数据库 CRUD 与相似度检索；理解 cosine similarity；理解 HNSW 等向量索引相比"全表扫描算内积"的优势；掌握向量数据库的 docker 化部署与多语言客户端调用。
- **技术选型决定**：使用 **Chroma**（`chromadb/chroma` 官方镜像）作为向量存储。理由：① 接口贴合 LangChain/LlamaIndex 行业标准，便于后续阶段5 接入网关层 / 阶段6 写架构文档时讲选型；② docker 一键起,跟现有 docker-compose 加一个 service 即可,运维成本低;③ 内置 HNSW 索引,几十万向量内毫秒级查询，远好于"MySQL JSON 列 + SQL 算内积"的 MVP（学习项目目的地数据虽然小，但用真实生产架构练手价值更高）。
- **项目实践**：
  - **docker-compose 新增 `chroma` 服务**（镜像 `chromadb/chroma:latest`，暴露 8000 端口，挂卷持久化）。
  - **依赖与配置**：安装 `chromadb` JS client；`.env` 增加 `CHROMA_URL=http://127.0.0.1:8000` 与 `CHROMA_COLLECTION=destinations_v1`。
  - **接口抽象**：新建 `src/rag/vectorStore.ts` 定义 `VectorStore` 接口（`add / query / delete`），实现 `ChromaVectorStore`；其他 RAG 模块只依赖接口，给后续切 Milvus/Qdrant 留口。
  - **EmbeddingFunction 注入**:把 Task 3.1 定义的 `Embedder` 接口包装成 chromadb 要求的 `EmbeddingFunction`(两者 `generate(texts)` 签名一致,几行 wrapper)注入 collection;**具体走哪个 embedder 由 `EMBEDDING_PROVIDER` 决定**(deterministic / xenova / minimax / openai),vectorStore 层不感知具体实现。
  - **Collection 配置**：`metadata: { "hnsw:space": "cosine" }`，对齐主流 RAG 实践。
  - **核心函数**：实现 `searchSimilarChunks(query: string, topK: number, filter?)`，支持元数据过滤（如 `where: { category: "scenery" }`）。
- **关联文件**：新增 `src/rag/vectorStore.ts`；修改 `docker-compose.yml`、`.env.example`、`package.json`（加 `chromadb` 依赖）。
- **输出物**：可运行的语义检索接口；Top-K 结果示例；一段"为什么选 Chroma 而非 MySQL JSON 列或 Milvus/Pinecone"的技术选型说明（写入 `docs/02-实验记录/exp-03-vectorstore-selection.md`，作为面试 STAR 素材）。

### Task 3.6:本地 Embedding 服务(Transformers.js + ONNX)
- **学习目标**:理解 ONNX 运行时在 JS 生态中的部署形态(进程内、零服务、零端口);掌握"换 provider 不动业务代码"的抽象有效性验证;具备把任意 HF 模型(只要有 Xenova/ONNX 版本)接入项目的能力。
- **背景说明**:Task 3.1 落地时 MiniMax 账号无 embedding 权限,临时走 `deterministic` 字符 n-gram 算法,流程能跑但无真语义(`exp-04` 实测 q2 "辣"无法匹配"火锅")。本任务把 embedding 切到真模型,只做**功能落地**,不做 deterministic/本地/云端三档对照实验(降低范围,聚焦"能跑")。
- **技术选型决定**:使用 **Transformers.js**(`@xenova/transformers`) + **Xenova/bge-small-zh-v1.5**(ONNX 量化版,512 维,~95MB)。理由:① **零外部服务**——直接在 Node 进程内跑 ONNX runtime,不需要额外 docker 容器、不占端口、不需要管 Ollama/TEI 这类后台进程;② **中文优化**——bge-small-zh-v1.5 是 BAAI 的中文专项轻量模型,对应我们旅游推荐场景的中文 query;③ **Xenova 仓库 ONNX 量化版**模型大小压缩到 ~95MB,Node 启动可接受;④ **完全离线**——首次运行自动下载到 `~/.cache/huggingface`,后续无网络依赖;⑤ **生态对齐**——`@xenova/transformers` 是 LangChain.js / LlamaIndex.ts 默认的本地 embedding 选项,面试讲选型有共识。
- **项目实践**:
  - **依赖**:`npm i @xenova/transformers`(自带 `onnxruntime-node`,无需额外装)。
  - **新增 `XenovaEmbedder`**(`src/rag/embedder.ts`):
    - 用 `pipeline('feature-extraction', modelId)` 加载模型,**lazy 单例**(首次 generate 时初始化,避免冷启动拖慢主流程)
    - 调用:`pipe(texts, { pooling: 'mean', normalize: true })` → 内部 mean pooling + L2 normalize,直接得到归一化向量
    - 维度查表:`Xenova/bge-small-zh-v1.5` = 512 维(写到 `MODEL_DIM_MAP` 便于切换其他 Xenova 模型如 gte-small 384 / bge-m3 1024 时一行扩展)
  - **`.env` 增加配置项**:
    - `EMBEDDING_PROVIDER=xenova`(切换入口)
    - `XENOVA_MODEL=Xenova/bge-small-zh-v1.5`(模型 id,可换其他 Xenova/* 模型)
  - **`config.ts`** zod 化:`EMBEDDING_PROVIDER` 枚举加 `'xenova'`;新增 `XENOVA_MODEL` 字符串字段
  - **`createEmbedder` 工厂**新增 `case 'xenova'` 分支
  - **重灌向量**:bge-small-zh-v1.5 是 512 维,跟当前 128 维 deterministic 不匹配,必须 `npm run index` 全量重灌(Chroma 会自动 drop 旧 collection 重建)
  - **smoke 验证**:跑 `npm run eval -- --case sem-01` 看模型能否正确选 `semantic_search_travel`(本任务不做完整对照,只验证流程通)
- **关联文件**:`src/rag/embedder.ts`、`src/config.ts`、`.env`、`.env.example`、`package.json`(加 `@xenova/transformers` 依赖)
- **关联八股**:
  - 03-RAG技术.md §3.1 embedding 模型选型(本地 ONNX 路径)
  - 08-工程化实践.md §5 多 Provider 抽象(本任务是抽象有效性的直接验证 —— deterministic → xenova 业务代码 0 改动)
- **关键决策与边界**:
  - ✅ **进程内 ONNX 而非独立服务**:跟 Ollama/TEI 的 docker 方案不同,Transformers.js 把模型加载到 Node 进程,适合学习项目"少一个运维点"的偏好
  - ✅ **lazy 单例初始化**:`getEmbedder()` 不会在启动时立即加载模型;`npm run dev` 启动仍然秒级;首次 RAG 调用慢 2~5s,后续推理快(本机 CPU 几十 ms)
  - ❌ **不做对照实验**:不写 `exp-05-embedding-comparison.md`,不跑 deterministic vs xenova 召回率对比表(聚焦"功能落地")
  - ⚠️ **内存代价**:Node 进程内存增加约 100~200MB(模型 + ONNX runtime),生产部署需注意
- **输出物**:可一键 `EMBEDDING_PROVIDER=xenova && npm run index` 切换到本地 ONNX embedding 的能力;一段"为什么选 Transformers.js 而不是 Ollama 独立服务"的技术选型说明(写入本规划或代码注释)。

### Task 3.7:联网搜索工具(Tavily)

## 阶段4：Agent 核心（第5周 ~ 第6周中，约2.5周）

### Task 4.5：Run 持久化、续流与三态中断
- **学习目标**：理解「HTTP 请求 ≠ Agent Run」的解耦原则；掌握长任务系统的事件回放、订阅恢复、三态 abort（被动断开 / 主动取消 / 系统关停）的工程实现；建立"Run-as-Resource"心智模型（对标 LangGraph runs / OpenAI Assistants threads）。
- **背景说明**：阶段1 的 abort 链路是 Chat App 思路（客户端关闭 = 整链终止），但 Agent 单次任务可能跑数分钟，用户切走/网络抖一下不应让 Run 终止、烧掉的 token 也不该浪费。本任务把"客户端断开"和"用户主动取消"拆成两种语义，并通过事件日志支持续订。
- **依赖**：阶段1 的 AbortController 与 token 统计；与 Task 4.3 共用 DB 持久层。
- **项目实践**：
  - **新增 `src/agent/runManager.ts`**：进程内 Run 注册表 + 事件总线 + 订阅者集合。提供 `start / subscribe / unsubscribe / cancel / getActive` 五个核心方法。
  - **三态 AbortController 模型**：
    - *Per-Subscriber Controller*：HTTP 请求级别，监听 `req.raw 'close'`，仅取消订阅、不影响 Run。
    - *Per-Run Controller*：RunManager 持有，仅在 ① POST `/runs/:runId/cancel`、② SIGTERM、③ Run 超时（默认 5 分钟）三种情况触发。
    - 两个 Controller 之间无级联——这是和阶段1 设计最关键的差异。
  - **新增 DB 表**（`src/db/migrations/003_agent_runs.sql`）：
    - `agent_runs(run_id, session_id, status, started_at, finished_at, last_event_seq, total_tokens)`
    - `agent_run_events(run_id, seq, event_json, created_at)`
    - 状态机：`pending → running → {completed | interrupted | cancelling → cancelled | failed}`
  - **新增 API**：
    - `GET /sessions/:id/runs/active` — 查最近未完成的 Run（前端打开会话时判断是否需要续订）
    - `GET /sessions/:id/runs/:runId/stream?after_seq=N` — 续订：先回放 N 之后的事件，再接实时流
    - `POST /sessions/:id/runs/:runId/cancel` — 用户主动中断（B 场景），202 Accepted，幂等
  - **重构现有 `POST /sessions/:id/stream`**：改为 `runManager.start + subscribe`；移除阶段1 的"req close → run abort"链路，改为"req close → unsubscribe only"。
  - **前端 UX 配套**：新增显式的「停止」按钮（区分被动断开与主动取消）；打开会话时先调 `/runs/active`，活跃则续订、否则走历史接口。
  - **可控降级**：进程重启后内存态 Run 丢失——重启时把 `running` 状态全标记为 `failed`，前端续订时显式提示"由于服务重启，本次任务已中断"。Redis Pub/Sub 跨进程方案推迟到 Task 5.4 容器化阶段。
- **关联文件**：
  - 新增 `src/agent/runManager.ts`、`src/db/runRepo.ts`、`src/db/migrations/003_agent_runs.sql`
  - 修改 `src/index.ts`（拆分 stream 接口、新增 cancel/active/resume 路由）

  - 修改 `web/src/api.ts`、`web/src/App.tsx`（新增停止按钮 + 续订流程）
- **关联八股**：
  - 02-核心框架.md ReAct 循环 / Run-as-Resource 模型
  - 05-记忆系统.md §短期记忆（事件流水 = episodic memory 的工程形态）
  - 08-工程化实践.md §1 容错（细粒度 abort 是熔断之外的另一种"防止失控"手段）/ §3 全链路可观测（事件日志即审计源）
- **输出物**：可演示的"切换会话不丢任务"效果；点击「停止」立即生效；带 seq 的事件回放（可被反复回放且与首次完全一致）；一段能讲清楚"为什么 HTTP 请求和 Run 必须解耦"的技术决策记录（对应面试 STAR 故事）。

### Task 5.5：LLM 网关层抽象（AI Gateway）
- **学习目标**：理解 AI 网关的定位与职责（统一接入、路由、缓存、限流、降级、可观测、合规），掌握中间件链式架构在 LLM 调用场景的落地方式；能讲清楚「自研轻量网关 vs LiteLLM/Portkey/Cloudflare AI Gateway 等成熟方案」的取舍。
- **背景说明**：当前 `src/agent/llm.ts` 直接耦合具体 Provider 协议，Task 1.2（token 统计）、5.2（模型路由）、5.3（容错监控）的能力分散在各处。本任务的目标是把这些跨切面能力**收口到一个网关层**，使业务代码（Agent、RAG、Planner）不再感知 Provider 差异。
- **项目实践**：
  - **接口抽象**：新建 `src/gateway/` 目录，定义统一接口 `LLMGateway.chat(req): Promise<ChatResponse>` 与流式接口 `chatStream(req)`，业务代码改为依赖该接口而非直连 Provider SDK。
  - **中间件链路**：实现可组合的中间件管道 `request → router → cache → ratelimit → provider adapter → retry → metrics → response`，每一层职责单一、可独立开关。
  - **多 Provider 适配器**：至少实现 2 个 adapter（如 MiniMax + OpenAI 兼容协议），通过配置切换，证明抽象有效。
  - **语义缓存 MVP**：复用阶段3的 embedding 能力，对入参 messages 做向量化，命中阈值（如 cosine ≥ 0.95）直接返回缓存响应；缓存可先用内存 LRU 或 MySQL 落盘。
  - **限流与配额**：基于 user_id / session_id 的滑动窗口限流；预留按 project 维度的预算上限（超额拒绝或降级到轻量模型）。
  - **统一可观测**：在网关入口生成 `trace_id`，串联 router 决策、cache 命中、retry 次数、provider 名、token 用量、总延迟；输出结构化日志。
  - **整合既有任务**：将 Task 5.2 的 router、Task 5.3 的 retry/metrics 重构为网关中间件而非散落在 `llm.ts`。

## 关键设计决策说明

1. **为什么从阶段2开始，阶段1只补 3~4 天？**
   项目已有 LLM 调用和 API 基础，阶段1的核心概念（Transformer、Token、参数）可通过「流式输出 + Token 统计」这两个小任务快速覆盖，不需要单独花整周时间。

2. **为什么 RAG 选 Chroma 而不是 MySQL JSON 列 或 Milvus/Pinecone？**
   三档方案的取舍：① **MySQL JSON 列**——0 依赖,但全表扫描无索引、不能讲 RAG 行业标准接口、性能在几千 chunk 就开始抖,**学完玩具感太强**;② **Milvus / Pinecone**——生产级别但运维 / 成本太重,跟我们"几百个目的地"的数据量完全不匹配,反而会让"为什么选 Milvus"无法自圆其说;③ **Chroma**——轻量(docker 一键起)、接口贴合 LangChain/LlamaIndex 生态、内置 HNSW 索引、能讲清楚选型理由——是学习项目里最贴近真实生产架构的甜蜜点。**接口仍然抽象成 `VectorStore`**(`src/rag/vectorStore.ts`),后续真有"亿级向量"需求,只换实现不动业务代码。这也对应面试问答集"技术选型不是越重越好,要匹配数据规模 + 团队成本"的思路。

3. **为什么阶段4要同时保留 ReAct 和 Plan-and-Execute？**
   面试问答集 Q1 就是「为什么选择 ReAct 而不是 Plan-and-Execute」。项目中同时实现两种模式并支持切换，既能深入理解两者差异，又能在面试中用实际数据（步骤数、耗时、完成率）支撑回答。

4. **为什么阶段4要把 Run 持久化（4.5）和记忆分层（4.3）绑在一起？**
   两者本质都在回答"什么状态需要跨连接、跨会话存活"——4.5 处理"事件流水"（episodic 记忆），4.3 处理"语义摘要"（semantic 记忆），共用 `agent_runs` 持久层、共用 `RUN_FINISHED` 触发时机。技术上 4.5 是 4.3 的底座（摘要生成需要订阅 Run 完成事件）；面试上这对组合能直接对应八股 05 §短期/长期记忆，是非常完整的故事点。同时 4.5 还纠正了阶段1"客户端断开即终止 Run"的 Chat App 心智，把项目从"对话工具"提升为"Run-as-Resource"的 Agent 系统——这是阶段3~5 工程化故事的关键转折。

5. **为什么阶段5要单独抽出 LLM 网关层（Task 5.5）？**
   网关层是大厂 LLM 应用必备的工程化能力，能在一处集中处理「统一接入、路由、缓存、限流、降级、可观测、合规」等跨切面问题。Task 1.2、5.2、5.3 的能力如果散落在 `llm.ts` 里，面试时只能讲点状能力；而把它们收口为一个网关，可以同时覆盖「架构分层」「中间件模式」「成本治理」「可观测性」「降级容错」5 个常考点，是性价比最高的工程化故事点。同时本任务也对应面试中「自研 vs LiteLLM/Portkey 等成熟方案如何取舍」的高频问题。

6. **为什么 Task 4.6 LangGraph 是"对照实现"而不是"切换替代"?**
   学习项目的最大资产是"手写每一层"换来的细节理解(ReAct 主循环、Run-as-Resource、三态 abort、AG-UI 协议、Few-shot 污染陷阱等)。直接切到 LangGraph 这些故事都没了,面试只能说"我用了 createReactAgent"。但完全不接 LangGraph 又会被问"你了解行业主流框架吗"——所以选**对照实现 + 双 backend 并存**:手写主线保留学习资产,LangGraph 复现拿"我也会用、且能讲清差异"的故事,二者通过 `AGENT_ENGINE` 配置切换,同测试集对比拿一手数据。这是面试性价比最高的 LangGraph 接入姿势。

7. **为什么 Task 3.6 / 3.7 把 embedding 本地化 + 加联网搜索?**
   Task 3.1 落地时 MiniMax 账号无 embedding 权限,临时用 `deterministic`(字符 n-gram)兜底,流程通但**无真语义**(`exp-04` 实测 q2 "辣"无法关联"火锅")。本地 embedding 走 Transformers.js + Xenova/bge-small-zh-v1.5(ONNX 量化版,中文专项,Node 进程内运行,零 docker 服务),跟现有 Embedder 抽象 1 行 `.env` 切换。联网搜索(Tavily)解决"知识库只有 3 个目的地"的玩具感——这两个任务一起让"RAG 全链路"从演示态升级为真实可演示的"能搜任意目的地 + 有真语义"系统,**为阶段4 MCP/Skills 提供更丰富的工具池**。

8. **为什么 Task 4.4 把 MCP 和 Agent Skills 绑在一起?**
   单独看 MCP 是协议升级(本地直调 → 跨进程调用),收益主要在工程层(工具复用、跨语言);单独看 Skills 是抽象升级(散乱 tool → 组合能力包),收益主要在模型层(决策复杂度降低)。**两者绑在一起讲**才能完整对应"工具(Tool)→ 工具集(Server)→ 技能(Skill)"三层抽象的演进——这是 2025 年 Agent 工程的最重要趋势,且能直接对接 Anthropic Agent Skills / Claude Code skills 等业界规范。

9. **每个阶段的「输出物」是什么？**
   每阶段至少产出：① 可运行的代码 + ② 笔记/实验记录 + ③ 一个能对外演示的效果。阶段6 产出简历条目和面试故事。
